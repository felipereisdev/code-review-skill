# Nuxt.js — Code Review Checklist

- **SSR vs CSR**: `useFetch`/`useAsyncData` used for server-side data fetching; client-only logic wrapped in `<ClientOnly>` or `onMounted`
- **Hydration mismatches**: no logic that produces different output on server vs client outside of client-only wrappers
- **Auto-imports**: components and composables use Nuxt auto-imports correctly; no manual imports that conflict
- **Route meta**: page-level meta (auth guards, layouts) defined via `definePageMeta`, not in middleware ad hoc
- **State**: `useState` used for SSR-safe shared state; Pinia for complex global state

## Precedents

- **`useFetch` and `useAsyncData` reuse server data on hydration**: a value that the handler returns during server rendering is stored in the page payload under the call's key, and the client call with the same key reads it instead of fetching again. Do not report them as fetching twice. **Exception:** a handler that returns `undefined` or `null` (for example one that forgets `return`), a key or options that differ between server and client (for example a key built from `Date.now()` or `Math.random()`), a custom `getCachedData` that returns `undefined`, and `$fetch` called directly in component setup, which runs on the server and again on the client.
- **`useState` gives each request its own state slot**: `useState(key, init)` keeps its value in the payload of the current server request and transfers it to the client, so each request gets a separate slot; it stores the result of `init` as is and does not clone it. Do not report it as leaking state between users when `init` allocates fresh data on every call (for example `() => ({ userId: null })`). **Exception:** an `init` that returns an object or array shared across calls, such as a module-scope constant, a cached value or a factory that returns the same instance, where mutating a nested property through `.value` changes the shared object for every later request, `ref` or `reactive` values declared at module scope (outside any function, for example at the top of a composable file), which the server shares across all requests, and other module-scope objects, arrays or caches that request code writes to.
- **Private `runtimeConfig` stays on the server**: keys outside the `public` and `app` namespaces of `runtimeConfig` are only available in server code. Do not report them as exposed to the browser. **Exception:** keys under `runtimeConfig.public` or `runtimeConfig.app`, which both reach the client, and private values that server code returns from an API route or puts into `useState` or the payload.
